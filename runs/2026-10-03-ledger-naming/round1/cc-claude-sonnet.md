## Ranked findings (biggest plan-changers first)

**1. [A — layout] The monorepo recommendation is overtaken by events that happened after it was written.**
`ledger-consolidation-2026-10-03.md` section 3.4 (lines 410-436) recommends one repo `PavolKum/fleet-economics` with `packages/claude-quota/` and `packages/fleet-ledger/`, reasoning partly on "there is no existing public repo to preserve" (line 432) and "the monorepo is free at exactly this moment and expensive later" (same line). That premise is now false: `next-steps.md`, Split-of-work item 1 (lines 22-24), records that by the time that file was last updated, `claude-quota-mcp` was already shipped as its **own standalone public repo** — `github.com/PavolKum/claude-quota-mcp`, tag `v0.2.0`, a CI workflow (`publish.yml`) wired to PyPI trusted publishing keyed to that exact repo name + workflow path, with only one pending web step (registering the trusted publisher on pypi.org) before release. Folding that into a monorepo subdirectory now means either breaking the existing URL/history continuity or doing extra migration work (re-pointing the trusted-publisher config, which is matched to repo+workflow path) for a package that was deliberately shipped standalone to be "the fastest public artefact ... the cleaner trust story." Tellingly, the consolidation doc's own "honest counter-argument" (line 436) already previewed this: *"If the reputation lens is the priority ... publish `PavolKum/claude-quota-mcp` standalone first ... That is the faster path to a public artifact, and it is the one I would take if forced to pick one thing to ship this week."* That is exactly what happened. The plan should follow the fact on the ground, not the stale recommendation.

Additional reason not in either doc: the ledger still needs a **destructive git-history rewrite** (orphan history or `filter-repo`, per `next-steps.md` line 9 and consolidation lines 449, both "Pavol's to run"). Doing that inside a monorepo that also holds the already-public, already-tagged `claude-quota-mcp` package means a mistake in the rewrite has blast radius against a tool that's already live and trusted. A brand-new, not-yet-public repo for the ledger has zero blast radius on the existing asset. That is a safety argument for separation, independent of audience/trust-story arguments.

The "why two packages, not one" reasons in consolidation 3.4 (lines 423-428: install-shape mismatch, trust asymmetry, zero shared code, different release cadence) are all real — but they argue for two *packages*, and apply with equal or greater force to two *repos*, since there is zero shared code or history between them to begin with. The "why one repo" case (lines 430-434) reduces, after the correction above, to one surviving point: a single README stating the "fleet economics" thesis is a nice reputation framing. That can be done with a short landing doc / cross-links between two repos (or, later, a thin docs-only repo) without re-housing a tool that already shipped.

Agent-discoverability (PyPI registries, model-facing docs, citation) is close to neutral here: a stranger agent finds either package by its own PyPI project page and description regardless of which GitHub repo backs it. This criterion doesn't swing the vote toward monorepo on its own.

**2. [D — sequencing, not mootness] The decision is not premature, but the plan should be explicit about what it does and doesn't unblock.**
Nothing here makes the naming/layout call moot to decide now — `next-steps.md`'s own Split-of-work item 2 already scopes "choose the new name" as agent-safe, reversible prep, correctly ordered *before* writing `pyproject.toml`/console-script/module names (so they aren't renamed twice). What *would* be premature is treating this decision as "the ledger is ready to ship": consolidation lines 447-452 list two still-open, harder blockers — the unpublishable 42-commit history (~290 MB of session-identifying data) and the fact that packaging metadata doesn't exist yet (no `pyproject`, no license, 20+ flat modules that collide on install, `build`/`hatchling` not installed) — plus a third lineage (`agent-usage`, consolidation line 395) that "is the same problem one layer down" and isn't even in scope yet. The 30-day measurement clock in `next-steps.md` (line 37) should be read as starting per-tool at actual PyPI publish, not at this naming decision; `claude-quota-mcp`'s own clock hasn't started yet either (PyPI step still pending). One secondary consequence of voting separate-repo on A: the name `fleet-economics` is freed up for a future umbrella/thesis artifact (landing page, docs repo) instead of being spent on the ledger's PyPI package name today — worth keeping in reserve rather than using now.

**3. [B — name] `fleet-ledger` is already the converging answer independent of the layout question.**
Consolidation 3.4 (line 414, and the diagram at 417-420) already proposes `fleet-ledger` as the PyPI name for this exact package, for reasons that hold regardless of monorepo-vs-separate-repo: it's short, it signals "pricing/usage tracking" (ledger) without tying to one harness (fleet), and it pairs cleanly with the sibling tool's name for a family story even across two repos. Of the five candidates, `agent-usage-ledger`/`agent-fleet-ledger` are more explicit but longer (18 chars vs. 12) with no real gain in clarity once the PyPI description does the explaining; `ai-fleet-ledger` adds a low-signal generic "ai-" prefix; `fleet-economics` is the right name for the *pair's thesis* (as consolidation itself uses it, for the repo/README, not the specific tool) and would undersell/overclaim scope if used for just the usage-pricing engine — and per point 2 above, it's better reserved for that umbrella role than spent here.

**4. [C — rename] No evidence favors renaming `claude-quota-mcp`; real evidence favors keeping it.**
It is already live and public under this name with a tag, CI, and a pending PyPI registration specifically keyed to the string `claude-quota-mcp` (consolidation's own diagram at line 420 keeps it unchanged: *"name unchanged, already in the README"*). Family branding, if wanted, belongs at the thesis/landing level (e.g., a "fleet economics" README or doc that links both tools by their real names), not by renaming an already-shipped trust-sensitive artifact.
